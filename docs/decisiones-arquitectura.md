# Decisiones de arquitectura - Control de Gasto Sistemas

Registro breve de decisiones tomadas y su motivo, para no perder el porqué con el tiempo.

| Fecha | Decisión | Motivo |
|---|---|---|
| Etapa 0 | Backend en FastAPI (Python) en vez de NestJS | Procesamiento de CSV y validaciones de datos más naturales en Python; Pydantic da contratos de datos y OpenAPI casi gratis |
| Etapa 0 | Frontend Next.js desplegado en Cloud Run (no Firebase Hosting) | Mantener todo el despliegue bajo un mismo modelo (Cloud Run + Artifact Registry + Terraform) |
| Etapa 0 | Moneda base: ARS | Definido por el usuario |
| Etapa 0 | Login MVP: usuario/contraseña propio, sin SSO | Definido por el usuario; 1 solo usuario en el MVP |
| Etapa 0 | Sin segregación de funciones (subir ≠ aprobar) | Definido por el usuario; 1 solo usuario en el MVP |
| Etapa 0 | Categorías y centros de costo tomados literalmente del CSV real de TSDocs (códigos ST01-ST08, STI03/05/06) | Evita inventar taxonomía; se aprovecha la clasificación contable ya existente en "Cuenta Personal" |
| Etapa 0 | "Cuenta Personal" se parsea en Categoría + Centro de Costo | Definido por el usuario, tras revisar el formato real `GRUPO - DESCRIPCIÓN - CÓDIGO` |
| Etapa 0 | Empresa y Sucursal como dimensiones filtrables nuevas | Definido por el usuario; permiten acumulados por razón social y por sede específica |
| Etapa 0 | "Sistemas Inversiones" tratado como categoría más, sin flag de CapEx | Definido por el usuario, para no sumar complejidad al MVP |
| Etapa 0 | Área "Seguridad" no se crea por separado; se computa en "Mesa de Servicio" | Definido por el usuario |
| Etapa 0 | Acumulado real por proveedor: neteo por Tipo de Documento (Factura/Fact. Crédito Pyme suman, Nota Crédito resta, Nota Débito suma) | Refleja el gasto real sin necesitar vincular manualmente cada nota a su factura de origen |
| Etapa 1 | Cloud SQL con IP pública + Cloud SQL Auth Proxy nativo de Cloud Run (sin VPC) | Simplifica la infraestructura para un MVP de 1 usuario; se puede migrar a IP privada + VPC connector más adelante si crece el equipo |
| Etapa 1 | CI/CD con clave de Service Account (JSON) en GitHub Secrets, no Workload Identity Federation | Más simple de configurar para el primer despliegue; queda anotado como mejora de seguridad futura |
| Etapa 1 | `tier = db-f1-micro`, `availability_type = ZONAL` en Cloud SQL | Dimensionado para 1 usuario; subir a un tier mayor y a REGIONAL si se suman más usuarios o se requiere alta disponibilidad |
| Etapa 3 | Se descarta el fuzzy matching (coincidencia difusa) para el mapeo de columnas del CSV/XLSX | Generaba falsos positivos (ej. "Vencimiento CAE" mapeaba como si fuera "Vencimiento"/plazo de pago). La normalización exacta (sin tildes, sin caracteres de control) ya cubre los casos reales encontrados |
| Etapa 3 | Sin tabla `exchange_rates`, sin `template_version_id` obligatorio en `import_batches` | Ya definido en el addendum #28 del diseño; el MVP usa un mapeo default hardcodeado (`app/services/mapping.py`) en vez de plantillas editables desde la UI |
| Etapa 3 | Aprobar una carga hace `db.flush()` factura por factura, no un solo INSERT masivo al final | Se detectó que la optimización automática de SQLAlchemy para INSERTs multi-fila (`insertmanyvalues`) generaba datos desalineados contra PostgreSQL con lotes grandes (460 filas). Insertar de a una fila es más lento pero elimina el riesgo; a la escala del MVP el impacto en performance es insignificante |
| Etapa 3 | Proveedores nuevos se crean automáticamente durante la importación (con alias), en vez de bloquear la carga | Coincide con la sección 8 del diseño ("no bloquear"); quedan marcados con advertencia `proveedor_creado_automaticamente` para que el validador los revise antes de aprobar |
| Etapa 3 | Driver de PostgreSQL: `psycopg` (v3) en vez de `psycopg2-binary` | En Windows, `psycopg2-binary` no tenía wheel precompilada para la versión de Python del equipo de desarrollo y pip intentaba compilarlo desde el código fuente (requiere `pg_config`, no instalado). `psycopg[binary]` (v3) sí publica wheels para versiones recientes de Python en Windows. Se probó de nuevo el flujo completo de importación con los 3 archivos reales tras el cambio, sin diferencias |
| Etapa 3 | `pandas`, `sqlalchemy`, `pydantic` con versión mínima (`>=`) en vez de fijada exacta (`==`) | Mismo problema que con `psycopg2-binary`: versiones exactas viejas no tenían wheel precompilada para la versión de Python de Windows del equipo, y pip intentaba compilar desde el código fuente (pandas requiere Meson + Visual Studio Build Tools). Se probó con las versiones más nuevas que instaló pip (pandas 3.0.2, SQLAlchemy 2.0.51, Pydantic 2.13.4) y todo sigue funcionando |
| Etapa 3 | Se reemplaza `passlib[bcrypt]` por `bcrypt` directo | `passlib` no tiene actualizaciones desde 2020 y es incompatible con `bcrypt >= 4.1` (error conocido: passlib hace un auto-test interno con una contraseña de más de 72 bytes que la API nueva de `bcrypt` rechaza en vez de truncar silenciosamente, y eso rompe el hashing de *cualquier* contraseña, no solo las largas). `bcrypt` por si solo es simple, mantenido activamente, y no depende de passlib |
| Frontend | Next.js 16 + React 19 en vez de Next.js 14 | La versión 14.2.5 original tenía una vulnerabilidad de DoS conocida (CVE-2025-55184/67779). En vez de perseguir parches sobre la rama 14.x (que sigue acumulando advisories), se saltó directo a la última versión estable mantenida activamente |
| Frontend | Tipografía: pila de fuentes del sistema, sin `next/font/google` | Cargar tipografías de Google Fonts requiere acceso a internet durante el build; para no depender de eso en cada build de CI/CD (y evitar una llamada externa más), se usa la pila nativa del sistema operativo (grotesca + monoespaciada) |
| Frontend | Token JWT guardado en `localStorage` (no cookie httpOnly) | Simplicidad para el MVP con 1 usuario. Es una debilidad conocida frente a XSS; si se agrega contenido de terceros a la aplicación en el futuro, conviene migrar a cookies httpOnly + CSRF token |
| Importación | `staging_invoices` separa `estado_fila` (clasificación de validación: válida/advertencia/error, fija) de `resultado` (decisión del usuario: pendiente/aprobada/rechazada, editable) | Pedido explícito: poder aprobar o rechazar factura por factura sin tener que resolver el lote completo de una vez. El estado del `import_batch` ya no se setea a mano, se recalcula (`recompute_batch_estado`) según cuántas filas siguen pendientes |
| Importación | Editar una factura en staging recalcula TODAS sus validaciones desde cero, incluido el chequeo de duplicado contra facturas ya aprobadas | Permite el caso de uso real: corregir un número de factura mal tipeado que generaba un falso duplicado, y que la advertencia desaparezca sola sin tener que rechazar la fila. El duplicado "dentro del mismo archivo" no se recalcula (requeriría recorrer todo el batch de nuevo); si era el único problema, el usuario revisa y aprueba a mano |
| Flujo de trabajo | A partir de esta etapa, todo el desarrollo se prueba en el entorno de Claude antes de entregarlo, y el despliegue va directo a producción (sin pasos de prueba en el Windows local del usuario) | Decisión del usuario: los problemas de Python 3.14/Windows/Docker en el entorno local consumían mucho más tiempo que el valor que aportaban; Cloud Run + Cloud SQL ya está probado y funciona de forma confiable |
